# ระบบลงเวลาปฏิบัติงาน (Hospital Smart Attendance) — Design

วันที่: 2026-11-10 · สถานะ: รอผู้ใช้ตรวจ · บันทึกการตัดสินใจ: `/mnt/project-files/attendance/decisions.md`

## เป้าหมาย

บุคลากรลงเวลาได้ภายในไม่กี่วินาที แต่ทุกครั้งที่ลงเวลาต้องมีหลักฐานที่ตรวจสอบย้อนหลังได้ (ใคร เมื่อใด ที่ไหน ด้วยวิธีใด ใครยืนยันหรืออนุมัติ) ทำเป็นโมดูล `attendance` ใน BackOffice (Next.js + TypeScript + MariaDB) ไม่แยกระบบ Laravel ตาม master prompt (ตัดสินข้อ 1)

หลักที่ใช้ทั้งโมดูล

1. เวลาอ้างอิงคือเวลา server เสมอ ผู้ใช้กำหนดเวลาเองไม่ได้ (ยกเว้นรายการออฟไลน์ ซึ่งเก็บเวลากล่องคู่กับเวลาที่ server รับ และเป็น "รอตรวจสอบ" เสมอ)
2. **รายการลงเวลา** เป็นข้อมูลต้นฉบับแบบเพิ่มอย่างเดียว ไม่มี UPDATE/DELETE (บังคับด้วย trigger ใน MariaDB) ผลตรวจ การยกเลิก และการปรับปรุงเป็นแถวใหม่ที่อ้างถึงต้นฉบับ
3. **ผลประเมินการลงเวลา** คำนวณจากต้นฉบับ + ผลตรวจ + รายการปรับปรุง + ตารางเวร + กฎ + ข้อยกเว้น (ลา ไปราชการ วันหยุด) ลบแล้วคำนวณใหม่ได้ทุกเมื่อโดยไม่กระทบต้นฉบับ
4. สิทธิ์ตรวจที่ server ทุก action ผ่าน `AuthorizationService` เท่านั้น
5. เก็บ UTC แสดงเวลาไทยและปี พ.ศ.

## ขอบเขตรอบแรก

อยู่ในรอบแรก: กล่องลงเวลา (Kiosk) สแกนหน้า 1:N, มือถือสแกน Dynamic QR + GPS เป็นทางสำรอง, รหัสบุคลากร + PIN, ทำงานออฟไลน์, ลงทะเบียนใบหน้า + ความยินยอม, ตารางเวรพื้นฐาน, เครื่องประเมิน, รายการรอตรวจสอบ, คำขอแจ้งลืมลงเวลา/คำอุทธรณ์การลงเวลา (2 ขั้น), ปิดรอบเดือน, dashboard 3 ระดับ, รายงาน 5 แบบ, ลบข้อมูลตามระยะเก็บ, audit แบบสายแฮช

นอกขอบเขต (รอบถัดไป): ลงเวลานอกสถานที่ (ข้อ 14), สลับเวร, OT และรายงาน OT, รายงานคำขอ/การอนุมัติ/ผิดปกติ/audit trail แบบส่งออกสำเร็จรูป, ไฟล์ PDF สร้างจาก server (รอบแรกใช้พิมพ์จากเบราว์เซอร์), NFC/เครื่องสแกนเดิม, เชื่อม HOSxP เพิ่มเติมนอกจากวันหยุดที่มีอยู่, Passkey/MFA (รอ SSO Provider ID)

|---|---|---|
| บุคลากร | ทุกบัญชีที่ใช้งาน | ลงเวลา ดูประวัติ/เวร/ผลประเมินของตน ยื่นคำขอแจ้งลืมลงเวลา/คำอุทธรณ์ ลงทะเบียนและถอนใบหน้าของตน |

| ผู้จัดการโมดูลลงเวลา | role `attendance-manager` (ผู้จัดการโมดูล) | ทุกหน่วยงาน: ตั้งประเภทเวรและกฎ ลงทะเบียนใบหน้าแทน ตั้ง PIN อนุมัติขั้นที่ 2 ปิดรอบเดือน รายงาน |
| ผู้ดูแลระบบ | `admin` เดิม | ลงทะเบียน/ถอนสิทธิ์กล่อง จุดลงเวลาและรัศมี GPS (และทุกอย่างที่ผู้จัดการโมดูลทำ ตามกติกาเดิม) |

## สถาปัตยกรรม

```
กล่อง Android (Chrome PWA /kiosk, กุญแจ ECDSA ที่ export ไม่ได้)
   │  HTTPS, ทุกคำขอลงนาม + idempotency key
   ▼
apps/web  /api/attendance/kiosk/*  ──►  packages/core/src/attendance  ──► MariaDB (attendance_*)
   ▲                                          │                        └► ที่เก็บไฟล์ส่วนตัวเดิม (ภาพ)
มือถือ (/attendance/scan, session ปกติ)       ├──► apps/face (Python, ภายในเท่านั้น, ไม่เก็บข้อมูล)
                                              └──► outbox → apps/worker (ประเมินใหม่, แจ้งเตือน, ลบตามระยะเก็บ)
```

### ส่วนประกอบ

- `packages/contracts/src/attendance.ts`: zod schema ของคำขอ/ผลลัพธ์ทุก endpoint, enum สถานะ, ประเภทเหตุการณ์
- `packages/core/src/attendance/`
  - `device-auth.ts` จับคู่กล่อง ตรวจลายเซ็นคำขอ (ECDSA P-256, ตรวจ timestamp ±60 วินาที และ nonce ไม่ซ้ำ)
  - `qr-challenge.ts` ออกและใช้ QR (HMAC-SHA256 ด้วย secret ฝั่ง server, อายุ 30 วินาที, ใช้ครั้งเดียว)
  - `geofence.ts` ระยะ haversine, ตรวจความแม่นยำและอายุตำแหน่ง
  - `face-matcher.ts` เทียบ embedding แบบ cosine กับ template ทุกคนที่ยินยอม คืน `identified | uncertain | unknown`
  - `pin-service.ts` hash ด้วย scrypt, นับผิดและล็อก
  - `clock-service.ts` จุดรวมการลงเวลาทุกช่องทาง (ตามขั้นตอนด้านล่าง)
  - `evaluation.ts` ฟังก์ชันบริสุทธิ์ คำนวณผลประเมินต่อช่วงเวร
  - `evaluation-service.ts` โหลดข้อมูล เรียก `evaluation.ts` เขียนผลแทนของเดิม
  - `roster-service.ts`, `review-service.ts`, `adjustment-service.ts`, `period-close-service.ts`, `report-service.ts`, `retention-service.ts`, `audit-chain.ts`
- `packages/db`: migration `0033_attendance.sql` (additive) + Drizzle schema `schema/attendance.ts`
- `apps/web`: หน้า `/kiosk` (ไม่อยู่ใต้ app shell), `/attendance/*`, API route ใต้ `/api/attendance/*`; เปลี่ยน entry `planned('attendance')` ใน `lib/modules.ts` เป็น live พร้อม sections
- `apps/face`: บริการ Python (FastAPI + InsightFace buffalo_l ONNX + โมเดล liveness แบบ passive) endpoint เดียว `POST /embed` รับภาพ JPEG คืน `{faces, embedding[512], liveness, quality}` ไม่เขียนดิสก์ ไม่ log ภาพ ฟังเฉพาะเครือข่ายภายใน ตรวจ shared secret ใน header; CI ใช้ตัวปลอมที่คืน embedding ตายตัว

### กล่องลงเวลา (Kiosk)

- ผู้ดูแลระบบสร้างกล่องที่จุดลงเวลาหนึ่งจุด ได้รหัสจับคู่ 8 หลัก ใช้ครั้งเดียว อายุ 10 นาที
- `/kiosk` บนกล่องสร้างคู่กุญแจ ECDSA P-256 ด้วย WebCrypto (`extractable: false`) เก็บใน IndexedDB ส่ง public key + รหัสจับคู่ server ผูกกุญแจกับกล่อง
- ทุกคำขอจากกล่องมี header `device-id`, `timestamp`, `nonce`, `signature` (ลงนามบน method + path + timestamp + nonce + SHA-256 ของ body) server ปฏิเสธเมื่อกล่องถูกถอนสิทธิ์ ลายเซ็นผิด เวลาเหลื่อมเกิน 60 วินาที หรือ nonce ซ้ำ
- กล่องส่ง heartbeat ทุก 60 วินาที ผู้ดูแลระบบเห็นสถานะออนไลน์และเวลาติดต่อล่าสุด
- token อุปกรณ์และลายเซ็นไม่ถูกเขียนลง URL, log, audit หรือ outbox

## ขั้นตอนลงเวลา (Attendance Engine)

ทุกช่องทางเรียก `ClockService.record()` ที่ทำตามลำดับ: ตรวจตัวตน/อุปกรณ์ → ตรวจสถานะบัญชีบุคลากร → ตรวจหลักฐานของช่องทาง → ตรวจ idempotency → อ่านเวลา server → ตัดสินเข้า/ออก → เขียน `attendance_event` + `attendance_event_evidence` + audit + outbox `attendance.event.recorded` ใน transaction เดียว → คืนผล การประเมินทำหลัง commit ผ่าน worker (ผลที่ตอบกลับทันทีคือสถานะของรายการ ไม่ใช่ผลประเมิน)

idempotency: ทุกคำขอมี `idempotency_key` (UUID ที่ client สร้างต่อการกดหนึ่งครั้ง) unique ใน `attendance_event` คำขอซ้ำได้ผลเดิมกลับ นอกจากนี้ใช้ `SELECT ... FOR UPDATE` บนแถว `attendance_person_lock` ของบุคลากร เพื่อให้คำขอพร้อมกันของคนเดียวกันตัดสินเข้า/ออกตามลำดับ และไม่สร้างสองรายการภายใน 60 วินาที (คำขอที่สองภายใน 60 วินาทีคืนรายการแรก)

### ช่องทาง

1. **สแกนหน้า (`FACE`)** กล่องตรวจจับหน้าในเครื่อง (ตรวจแค่ว่ามีหน้า) แล้วส่งภาพ server เรียก `apps/face` → liveness ต้องผ่านเกณฑ์ → เทียบกับ template: `identified` เมื่อคะแนนสูงสุด ≥ เกณฑ์สูง และห่างอันดับสองอย่างน้อยค่าส่วนต่าง (ตั้งค่าได้ ค่าเริ่มต้นกำหนดหลังทดสอบกับภาพจริงของโรงพยาบาลในงานที่ 4) ผล = `ACCEPTED` กรณี `uncertain`/`unknown`/liveness ไม่ผ่าน: ไม่สร้างรายการลงเวลา กล่องขึ้น "ใช้ PIN หรือมือถือ" และบันทึก `attendance_security_event` (เก็บภาพไว้เป็นหลักฐานตามระยะเก็บ)
2. **มือถือสแกน QR (`MOBILE_QR`)** กล่องแสดง QR ที่มุมจอตลอด เปลี่ยนทุก 30 วินาที (`attendance_qr_challenge`) บุคลากร login บนมือถือ เปิด `/attendance/scan` สแกนด้วยกล้องในหน้าเว็บ (QR บรรจุ token ล้วน ไม่ใช่ URL; token ส่งใน body) พร้อม GPS (`lat`, `lng`, `accuracy`, `positionTimestamp`) server ตรวจ: token ถูกต้อง ไม่หมดอายุ ไม่เคยใช้ (ใช้แล้วทำเครื่องหมายใน transaction เดียวกัน) → ระยะจากจุดลงเวลา ≤ รัศมี → accuracy ≤ 50 ม. → อายุตำแหน่ง ≤ 60 วินาที แล้วส่งคำสั่งถ่ายภาพให้กล่อง (กล่อง poll ทุก 2 วินาที) ภาพผูกกับรายการเมื่อมาถึง ผล: บุคลากรที่ไม่มี template ใบหน้า + ผ่านทุกข้อ = `ACCEPTED`; มี template ใบหน้า (คือใช้เป็นทางสำรอง) หรือ GPS ไม่ผ่านข้อใด = `PENDING_REVIEW` พร้อม risk flag; token ไม่ถูกต้อง/หมดอายุ/ใช้ซ้ำ = ไม่สร้างรายการ ตอบข้อผิดพลาดและบันทึก security event
3. **รหัสบุคลากร + PIN (`KIOSK_PIN`)** กล่องถ่ายภาพทุกครั้ง PIN ถูก = `PENDING_REVIEW` PIN ผิด = ไม่สร้างรายการ นับผิด 5 ครั้งใน 15 นาที → ล็อกรหัสนั้น 15 นาที และจำกัดอัตรา 30 ครั้ง/นาที/กล่อง ไม่บอกว่ารหัสบุคลากรมีอยู่จริงหรือไม่
4. **ออฟไลน์ (`KIOSK_OFFLINE`)** เมื่อกล่องติดต่อ server ไม่ได้ จอขึ้นแถบ "ออฟไลน์" รับรหัส + PIN + ภาพ + เวลากล่อง เก็บใน IndexedDB ลงนามด้วยกุญแจกล่องแต่ละรายการ กล่องไม่มี PIN hash ของใคร เมื่อออนไลน์ส่งเป็นชุด server ตรวจลายเซ็นและ PIN: ถูก = `PENDING_REVIEW` (risk flag `OFFLINE`) ผิด = `REJECTED` ทุกรายการเก็บ `client_timestamp` และ `server_received_at`; `occurred_at` = เวลากล่อง ยกเว้นกล่องเวลาเหลื่อมจาก server ตอนกลับมาออนไลน์เกิน 2 นาที → flag `CLOCK_DRIFT`

### ตัดสินเข้า/ออก (ข้อ 15)

หาช่วงเวรปัจจุบันของบุคลากร (ช่วงที่เวลานี้อยู่ใน [เริ่ม − หน้าต่างก่อนเริ่ม, เลิก + หน้าต่างหลังเลิก]) ถ้าไม่มีรายการเข้าที่นับได้ในช่วงนั้น = `IN` มีแล้ว = `OUT` ไม่มีช่วงเวร = สลับตามรายการล่าสุดภายใน 16 ชั่วโมง ถ้าจะเป็น `OUT` ภายใน 5 นาทีหลัง `IN` กล่องถามยืนยันก่อน (ปุ่มใหญ่ "ใช่ ลงเวลาออก" / "ยกเลิก")

### ผลบนจอกล่อง

แสดง 3 วินาที: ✓ ลงเวลาเข้า/ออก, เวลา server, ชื่อ, หน่วยงาน, ชื่อเวร หรือ "รอหัวหน้าตรวจสอบ" สำหรับ `PENDING_REVIEW` ปุ่ม "ไม่ใช่ฉัน" สร้าง `attendance_event_void` ที่อ้างรายการนั้น (รายการยังอยู่ ผลประเมินไม่นับ) บันทึก security event `MISIDENTIFIED` แล้วเปิดหน้า PIN

### รายการรอตรวจสอบ

หัวหน้าหน่วยงานของบุคลากร (หรือผู้จัดการโมดูล) เห็นรายการ `PENDING_REVIEW` พร้อมภาพ ช่องทาง risk flag และเวลา กด "ยืนยัน" หรือ "ไม่ยืนยัน" (ต้องมีเหตุผล) ใน ActionDialog → แถวใหม่ใน `attendance_event_review` + audit + outbox ในหนึ่ง transaction บุคลากรยืนยันรายการของตัวเองไม่ได้ ยกเว้นตามกติกา `canDecideOwnRequest` (admin/manager tier ต้องมีเหตุผล audit มี `selfApproval: true`) รายการที่ไม่มีผลตรวจไม่นับในผลประเมิน และแสดงเป็น "รอตรวจสอบ"

## ตารางเวรและการประเมิน (ข้อ 8, 12)

- **ประเภทเวร** (`attendance_shift_type`): ชื่อ เวลาเริ่ม เวลาเลิก (เลิก ≤ เริ่ม = ข้ามวัน) หน้าต่างก่อนเริ่ม (ค่าเริ่มต้น 60 นาที) ช่วงผ่อนผันมาสาย (0) ช่วงผ่อนผันกลับก่อน (0) เวลารอลงออกหลังเลิก (240 นาที) สี ป้าย เปิด/ปิดใช้ seed: ราชการปกติ 08:30–16:30, เช้า 08:00–16:00, บ่าย 16:00–00:00, ดึก 00:00–08:00, ข้ามวัน 20:00–08:00 แก้ได้ทั้งหมด
- **การจัดเวร** (`attendance_shift_assignment`): บุคลากร วันที่เริ่มเวร ประเภทเวร (หนึ่งคนหลายเวรในวันเดียวได้) ห้ามช่วงเวลาซ้อนกัน (ตรวจตอนบันทึก) แก้/ลบได้โดยหัวหน้า ผู้จัดเวร หรือผู้จัดการโมดูล ทุกการเปลี่ยนเข้า audit และสั่งประเมินช่วงนั้นใหม่ เดือนที่ปิดรอบแล้วแก้ได้เฉพาะผู้จัดการโมดูล
- **ไม่มีการจัดเวร**: วันทำการ (จันทร์–ศุกร์ ที่ไม่ใช่วันหยุดราชการ) ถือว่ามีเวร "ราชการปกติ" สำหรับบุคลากรที่หน่วยงานตั้งเป็น "ไม่ใช้ตารางเวร" (ค่าเริ่มต้น) หน่วยงานที่ตั้ง "ใช้ตารางเวร" ไม่มีเวรเริ่มต้น
- **ช่วงเวร**: การจัดเวรที่ต่อกันพอดี (เลิก = เริ่มของถัดไป) รวมเป็นช่วงเดียว
- **กฎประเมิน** (`evaluation.ts`, ฟังก์ชันบริสุทธิ์): รายการที่นับ = `ACCEPTED` ที่ไม่ถูกยกเลิก + `PENDING_REVIEW` ที่ยืนยันแล้ว + รายการปรับปรุงจากคำขอที่อนุมัติ (รายการปรับปรุงแทนที่รายการต้นฉบับที่มันอ้าง) ในหน้าต่างของช่วงเวร ครั้งแรก = เข้า ครั้งสุดท้าย = ออก
  - `late_minutes` = max(0, เข้า − (เริ่ม + ผ่อนผัน)) นาที; `early_minutes` = max(0, (เลิก − ผ่อนผัน) − ออก)
  - สถานะ (หนึ่งค่า + ตัวเลขนาทีกำกับเสมอ): `LEAVE` / `TRAVEL` (มีคำขอลา/ไปราชการที่อนุมัติครอบช่วงเวร; ลาครึ่งวันครอบเฉพาะครึ่งที่ลา) → `HOLIDAY` (เวรเริ่มต้นราชการปกติในวันหยุด ไม่สร้างช่วงเวรเลย) → `PENDING_REVIEW` (มีรายการรอตรวจสอบในหน้าต่าง) → `ABSENT` (ไม่มีเข้า และหน้าต่างหลังเลิกผ่านไปแล้ว) → `MISSING_OUT` (มีเข้า ไม่มีออก และหน้าต่างหลังเลิกผ่านไปแล้ว) → `LATE` / `EARLY_LEAVE` / `LATE_AND_EARLY` → `NORMAL` → `IN_PROGRESS` (ช่วงยังไม่จบ)
  - รายการที่ไม่อยู่ในหน้าต่างช่วงเวรใด = `OFF_SHIFT` (ผลแยก ใช้ในรอบ OT)
- **คำนวณใหม่**: worker รับ outbox `attendance.event.recorded`, `attendance.event.reviewed`, `attendance.adjustment.approved`, `attendance.roster.changed`, `leave.request.decided`, `travel.request.decided`, holiday sync แล้วคำนวณช่วงเวรที่เกี่ยวข้อง และงานรอบทุก 15 นาทีปิดช่วงที่หน้าต่างหลังเลิกผ่านไป (ให้ ABSENT/MISSING_OUT เกิดตรงเวลา) `attendance_evaluation` เป็นข้อมูลอนุพันธ์ เขียนทับได้ เก็บ `rule_version` และ `computed_at`

## คำขอแจ้งลืมลงเวลาและคำอุทธรณ์การลงเวลา (ข้อ 10)

- ใช้ระบบคำขอ/สายอนุมัติกลางเดิม (`workflow`) ประเภทคำขอ `attendance-missed` (แจ้งลืมลงเวลา: ขอเพิ่มเวลาเข้าและ/หรือออก) และ `attendance-appeal` (คำอุทธรณ์การลงเวลา: ขอให้ไม่นับหรือแทนเวลาของรายการหนึ่ง พร้อมเวลาที่ถูกต้อง)
- ฟอร์มใน FormDialog: วันที่ของช่วงเวร (เลือกจากปฏิทิน; ถ้ามีวันเริ่ม/สิ้นสุด วันสิ้นสุดตั้งเป็นวันเริ่มอัตโนมัติ) เวลาเดิม (ระบบเติมให้) เวลาที่ขอ เหตุผล (บังคับ) ไฟล์แนบหลักฐาน (ไฟล์แนบส่วนตัวเดิม ไม่บังคับ)
- ยื่นได้ภายใน 30 วันหลังวันเวร (ตั้งค่าได้) สายอนุมัติ: ขั้น 1 หัวหน้าหน่วยงาน → ขั้น 2 ผู้จัดการโมดูลลงเวลา ทุกคำขอ มีส่งกลับแก้ไข แจ้งเตือนกระดิ่ง + LINE ตามระบบเดิม (ข้อความไม่มีเหตุผลหรือรายละเอียดหลักฐาน)
- อนุมัติขั้นสุดท้าย → `attendance_adjustment` (อ้างคำขอ และอ้างรายการต้นฉบับถ้ามี) + audit + outbox ใน transaction เดียว ไม่แตะ `attendance_event`
- **ปิดรอบเดือน**: ผู้จัดการโมดูลปิดรอบเดือนหนึ่ง (ActionDialog) หลังปิด การจัดเวรของเดือนนั้นแก้ได้เฉพาะผู้จัดการโมดูล และรายงานแสดง "ปิดรอบแล้ว" พร้อมเวลาและผู้ปิด

## ใบหน้า ความยินยอม และ PIN (ข้อ 3, 5, 6, 7)

- **ลงทะเบียนเอง**: บุคลากรเปิด "ลงทะเบียนใบหน้า" ในหน้าของฉันบนมือถือ อ่านข้อความแจ้งวัตถุประสงค์ ระยะเก็บ สิทธิถอน แล้วกดยินยอม (บันทึก `attendance_face_consent` ฉบับข้อความที่แสดง) → สแกน QR ที่กล่อง → กล่องเข้าโหมดลงทะเบียนให้บุคคลนั้น 60 วินาที ถ่าย 5 ภาพ → server เรียก `apps/face` ทุกภาพต้องมีหน้าเดียว คุณภาพผ่าน และ liveness ผ่าน → template = ค่าเฉลี่ย embedding ที่ normalize แล้ว เข้ารหัส AES-256-GCM ด้วยกุญแจจาก env (`ATTENDANCE_FACE_KEY_FILE`) ใช้ได้ทันที
- **HR ลงทะเบียนให้** (คนไม่มีมือถือ): ผู้จัดการโมดูลเลือกบุคลากร ยืนยันว่ามีใบยินยอมกระดาษที่ลงนามแล้ว (แนบสแกนเป็นไฟล์แนบส่วนตัว) แล้วสั่งกล่องเข้าโหมดลงทะเบียน หรือถ่ายด้วยกล้องเครื่องที่ใช้งาน
- **ถอนความยินยอม**: บุคลากรกดเองในหน้าของฉัน (ActionDialog) → ลบ template และภาพลงทะเบียนทันที บันทึกการถอนใน consent และ audit (ไม่มีข้อมูลใบหน้าใน audit)
- **PIN**: 6 หลัก ผู้จัดการโมดูลตั้งให้ (แสดงครั้งเดียว) บุคลากรเปลี่ยนเองได้ในหน้าของฉัน เก็บเป็น scrypt hash
- ผู้ไม่ยินยอมใช้มือถือ QR + GPS ได้ตามปกติ และไม่ถือว่าผิดปกติ

## ระยะเก็บข้อมูล (ข้อ 13)

| ข้อมูล | ระยะเก็บ (ตั้งค่าได้) |
|---|---|
| ภาพตอนลงเวลา ภาพหลักฐาน ภาพ security event | 365 วัน แล้วลบไฟล์ (ภาพที่ผูกกับรายการรอตรวจสอบหรือคำขอที่ยังไม่จบ เก็บจนจบ) |
| พิกัด GPS | 365 วัน แล้วล้างค่า lat/lng เหลือผล `inside`/`outside` และ accuracy |
| template + ภาพลงทะเบียนใบหน้า | จนถอนความยินยอม หรือ 365 วันหลังพ้นสภาพบุคลากร |
| รายการลงเวลา ผลตรวจ รายการปรับปรุง ผลประเมิน audit | ถาวร |

หลักฐานที่ลบตามระยะเก็บอยู่ในตารางลูก (`attendance_event_evidence`, `attendance_photo`) ไม่ใช่ใน `attendance_event` trigger ห้ามแก้จึงไม่ขัดกับการลบตามระยะเก็บ งานลบรันใน worker วันละครั้ง และเขียน audit จำนวนที่ลบ ตัวเลขควรให้ DPO ยืนยันก่อนใช้จริง

## Audit แบบสายแฮช

`attendance_audit_chain` เก็บต่อจาก audit เดิมของทุก action ในโมดูล: `seq`, `audit_event_id`, `prev_hash`, `hash` = SHA-256(prev_hash ‖ canonical JSON ของ audit event) เขียนใน transaction เดียวกับ audit (ล็อกแถวล่าสุดด้วย `FOR UPDATE`) ผู้ตรวจสอบกด "ตรวจสอบความต่อเนื่อง" ระบบไล่ทั้งสายและรายงานแถวแรกที่ไม่ตรง trigger ห้าม UPDATE/DELETE ทั้ง `attendance_event`, `attendance_event_review`, `attendance_event_void`, `attendance_adjustment`, `attendance_audit_chain` metadata ของ audit ไม่มีเหตุผลการตัดสิน PIN token ภาพ พิกัด หรือข้อมูลใบหน้า (ตามกติกา CLAUDE.md)

## หน้าจอ

ทุกฟอร์มเพิ่ม/แก้/ลบเปิดใน FormDialog และทุกการยืนยันใน ActionDialog ปิดได้ด้วยปุ่มเท่านั้น ข้อความ validation ภาษาไทย ทุกหน้ามี loading/empty/error state ตาม DESIGN.md

- `/kiosk` (เต็มจอ ไม่มี app shell): นาฬิกา server ขนาดใหญ่ (ซิงก์ทุก 60 วินาที) วันที่ พ.ศ. ภาพกล้อง กรอบผล 3 วินาที ปุ่ม "ไม่ใช่ฉัน" "ใช้รหัส + PIN" QR มุมขวาล่าง แถบออฟไลน์พร้อมจำนวนรายการค้างส่ง หน้าจับคู่เมื่อยังไม่ลงทะเบียน
- `/attendance` (ของฉัน): ชื่อ หน่วยงาน วันที่ เวลา server เวรวันนี้ ปุ่ม "สแกนลงเวลา" (ไป `/attendance/scan`) ผลประเมินล่าสุดพร้อมนาทีสาย/กลับก่อน ประวัติรายการ (ช่องทาง สถานะ) ปุ่ม "แจ้งลืมลงเวลา" "อุทธรณ์" สถานะคำขอ ใบหน้า (ลงทะเบียน/ถอน) เปลี่ยน PIN
- `/attendance/scan`: สแกน QR ด้วยกล้อง ขอตำแหน่ง แสดงสถานะ GPS (อยู่ในพื้นที่/ความแม่นยำ) และผล
- `/attendance/unit`: ตัวเลขวันนี้ (มีเวร ลงแล้ว ยังไม่ลง รอตรวจสอบ คำขอรออนุมัติ) รายคน ตัวเลือกหน่วยงาน (เฉพาะที่มีสิทธิ์)
- `/attendance/review`: รายการรอตรวจสอบพร้อมภาพ (เปิดภาพผ่าน endpoint ที่ตรวจสิทธิ์)
- `/attendance/roster`: ตารางเวรรายเดือน (คน × วัน) เลือกประเภทเวรต่อช่อง แจ้งเวรซ้อน
- `/attendance/hr`: ภาพรวมทั้งโรงพยาบาล รายหน่วยงาน เหตุการณ์ผิดปกติ คำขอ
- `/attendance/reports`: รายงาน 5 แบบ (ประจำวัน ประจำเดือนรายคน แยกหน่วยงาน ผู้ยังไม่ลงเวลา มาสาย/กลับก่อนพร้อมนาที) ส่งออก Excel (`xlsx`) และหน้าพิมพ์ ทุกรายงานมีหัวรายงาน วันที่สร้าง ผู้สร้าง และเงื่อนไขที่ใช้ การส่งออกใช้สิทธิ์ `data.export` + audit ตามแบบเดิม
- `/attendance/settings`: ประเภทเวรและกฎ หน่วยงานใช้ตารางเวร ค่าตั้ง ใบหน้า (HR ลงทะเบียนให้) PIN ปิดรอบเดือน
- `/attendance/devices`: กล่อง (สร้าง รหัสจับคู่ ถอนสิทธิ์ สถานะออนไลน์) จุดลงเวลา (แผนที่พิกัด + รัศมี)
- `/attendance/audit`: audit ของโมดูล ตรวจความต่อเนื่องของสายแฮช ส่งออก

Dashboard ทุกตัวเลขมาจาก query จริง ข้อมูลตัวอย่างใน development มาจาก seed ที่ระบุชัดว่าเป็นข้อมูลจำลอง ไม่มีบุคลากรหรือผู้ป่วยจริง

## การจัดการข้อผิดพลาด

- รหัสข้อผิดพลาดของ API (ใน contracts): `DEVICE_REVOKED`, `DEVICE_SIGNATURE_INVALID`, `REQUEST_REPLAYED`, `QR_EXPIRED`, `QR_USED`, `QR_INVALID`, `OUTSIDE_AREA`, `GPS_INACCURATE`, `GPS_STALE`, `PIN_INVALID`, `PIN_LOCKED`, `FACE_NOT_RECOGNIZED`, `FACE_LIVENESS_FAILED`, `FACE_SERVICE_UNAVAILABLE`, `PERSON_INACTIVE`, `SHIFT_OVERLAP`, `PERIOD_CLOSED`, `REQUEST_TOO_OLD`, `CONFLICT_OF_INTEREST` แต่ละตัวมีข้อความไทยใน `packages/i18n`
- `apps/face` ล่มหรือช้าเกิน 3 วินาที: กล่องขึ้น "ใช้รหัส + PIN หรือมือถือ" ไม่ถือว่าออฟไลน์
- transaction ล้มเหลว: ไม่มีข้อมูลค้างครึ่งเดียว ผู้ใช้เห็น "ลงเวลาไม่สำเร็จ ลองใหม่" และกดซ้ำได้อย่างปลอดภัยด้วย idempotency key เดิม

## การทดสอบ

ทุกงานเขียนเทสต์ที่ล้มก่อน (TDD) และรายงานผลจริง; integration test ต้องมี `DATABASE_URL` (ข้ามเมื่อไม่มี และต้องรายงานว่าข้าม)

- Unit: `evaluation.ts` (เวรปกติ ข้ามเที่ยงคืน 20:00–08:00 เวรต่อกัน มาสาย/กลับก่อนพร้อมนาที ผ่อนผัน ขาด ลืมลงออก วันหยุด ลาเต็มวัน/ครึ่งวัน ไปราชการ รายการปรับปรุงแทนต้นฉบับ รายการถูกยกเลิก รอตรวจสอบ นอกเวร) `geofence.ts` `qr-challenge.ts` `face-matcher.ts` (identified/uncertain/unknown, margin) `device-auth.ts` (ลายเซ็นผิด เวลาเหลื่อม nonce ซ้ำ) `audit-chain.ts` (ตรวจพบการแก้แถวกลางสาย)
- Integration (MariaDB): QR หมดอายุ ใช้ซ้ำ ส่งพร้อมกัน 2 คำขอได้ใช้แค่หนึ่ง; idempotency กดซ้ำได้รายการเดียว; 10 คำขอพร้อมกันของคนเดียวได้รายการเดียว; กล่องถูกถอนสิทธิ์; PIN ผิด 5 ครั้งล็อก; ออฟไลน์ชุดส่งย้อนพร้อม PIN ผิดหนึ่งรายการ; trigger ห้าม UPDATE/DELETE `attendance_event`; transaction ล้มกลางทางไม่เหลือรายการ/audit/outbox; หัวหน้าดูและยืนยันต่างหน่วยงานไม่ได้; ผู้จัดเวรอนุมัติไม่ได้; ผู้ตรวจสอบแก้ไม่ได้; บุคลากรลงเวลาแทนคนอื่นไม่ได้ (person มาจาก session/การระบุตัวเท่านั้น); แก้ตารางเวรย้อนหลังแล้วประเมินใหม่; เดือนปิดรอบแก้เวรไม่ได้ยกเว้นผู้จัดการโมดูล; คำขอ 2 ขั้นอนุมัติ/ไม่อนุมัติ/ส่งกลับ และรายการปรับปรุงเกิดเฉพาะเมื่ออนุมัติขั้นสุดท้าย; ถอนความยินยอมลบ template; งานลบตามระยะเก็บ; รีสตาร์ต worker แล้วประเมินต่อได้ (outbox)
- Web: หน้า `/kiosk` (ผล, ไม่ใช่ฉัน, PIN, ออฟไลน์คิว) และหน้า popup ด้วย Testing Library; Playwright เดินครบวงจร: จับคู่กล่อง → มือถือสแกน QR (ตำแหน่งจำลอง) → หัวหน้ายืนยัน → ผลประเมิน
- `apps/face`: pytest กับภาพสังเคราะห์ (ไม่มีภาพบุคคลจริงใน repo) และขั้นทดสอบแม่นยำแยกด้วยภาพอาสาสมัครที่ยินยอม บนเครื่องโรงพยาบาลเท่านั้น
- Backup/restore: เพิ่มตาราง attendance ในการตรวจ `infra/backup/restore-verify.test.sh`

## ลำดับส่งมอบ (PR ละงาน merge ได้ทีละอัน)

1. ฐาน: migration + schema, contracts, permission + role ใหม่, audit สายแฮช, ประเภทเวร/กฎ/ค่าตั้ง, จุดลงเวลา, กล่อง + จับคู่ + ตรวจลายเซ็น, entry โมดูลเป็น live ในโหมดพัฒนา
2. ตารางเวร + `evaluation.ts` + evaluation service + worker
3. ช่องทาง QR + GPS, PIN, หน้า Kiosk, หน้าของฉัน/สแกน, รายการรอตรวจสอบ → ใช้งานได้ครบวงจรครั้งแรก
4. `apps/face` + ลงทะเบียนใบหน้า (เอง/HR) + ความยินยอม + สแกนหน้าที่กล่อง + ไม่ใช่ฉัน
5. ออฟไลน์
6. คำขอแจ้งลืมลงเวลา/คำอุทธรณ์ 2 ขั้น + รายการปรับปรุง + ปิดรอบเดือน
7. Dashboard หน่วยงาน/HR + รายงาน 5 แบบ + งานลบตามระยะเก็บ + เอกสารติดตั้ง (บริการใบหน้า กล่อง Android) ภาษาไทย

## ความเสี่ยงและข้อจำกัด

- ความแม่นยำของ 1:N ขึ้นกับจำนวนคนและคุณภาพกล้อง เกณฑ์ต้องปรับด้วยข้อมูลจริงก่อนเปิดใช้ (เปิดโมดูลในโหมดพัฒนา/นำร่องก่อน)
- liveness แบบภาพเดียวกันรูปถ่ายได้ระดับหนึ่ง ไม่กันหน้ากาก 3D ได้ หลักฐานภาพทุกครั้งช่วยตรวจย้อนหลัง
- GPS ปลอมได้บนเครื่องที่ root ช่องทางมือถือจึงพึ่ง QR ที่ต้องอยู่หน้ากล่องร่วมด้วย
- กุญแจกล่อง export ไม่ได้ผ่าน WebCrypto แต่ผู้ที่ควบคุมกล่องได้ยังใช้กุญแจลงนามได้ ต้องติดตั้งกล่องในที่มีคนเห็นและถอนสิทธิ์ได้ทันที
- ข้อมูลชีวมิติเป็นข้อมูลอ่อนไหวตาม PDPA ต้องให้ DPO อนุมัติข้อความยินยอมและระยะเก็บก่อนเปิดใช้จริง
