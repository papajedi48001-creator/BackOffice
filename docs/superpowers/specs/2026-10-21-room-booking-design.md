# Room Booking Design (R3 ห้องประชุม)

**Status:** draft for review
**Date:** 2026-10-21
**Source:** คำขอของผู้ใช้ในเธรด "ระบบจองห้องประชุม" และการสัมภาษณ์ออกแบบ 11 ข้อ (2026-10-21)
**Related:** `docs/adr/0001-room-booking-own-lifecycle.md`, `docs/adr/0002-room-booking-auth-seam.md`

## Purpose

ให้บุคลากรจองห้องประชุมผ่าน Back Office ได้เอง เห็นปฏิทินห้องออนไลน์ และให้ธุรการพิจารณาการจองทุกรายการ โดยมีเลขอ้างอิง ประวัติการจอง เหตุผล และบันทึกการตรวจสอบครบ ผู้จองได้รับแจ้งทุกขั้นตอน

## Decisions from the interview

| # | เรื่อง | ข้อสรุป |
|---|---|---|
| 1 | นโยบายการอนุมัติ | ทุกห้องต้องอนุมัติก่อน ไม่มีการยืนยันอัตโนมัติ |
| 2 | ผู้อนุมัติ | ธุรการกลางชุดเดียว ขั้นเดียว ใช้บทบาท `room-booking-approver` ใครถือบทบาทนี้ก็พิจารณาได้ |
| 3 | จองหลายวัน | การจองเดียว ช่วงเวลาเดียวกันทุกวัน อนุมัติหรือปฏิเสธทั้งชุด |
| 4 | การกันเวลา | กันทันทีเมื่อยื่น ใครยื่นก่อนได้ก่อน จนกว่าจะถูกปฏิเสธหรือยกเลิก |
| 5 | รายการเสริม | ผู้จัดการห้องประชุมตั้งรายการเอง ผู้จองเลือกพร้อมจำนวนและหมายเหตุ อนุมัติไปพร้อมการจอง |
| 6 | การยกเลิก | ต้องมีเหตุผลเสมอ ผู้จองยกเลิกทั้งชุดได้ก่อนเริ่ม หรือคืนวันที่ยังไม่เริ่มเมื่อเริ่มใช้แล้ว ผู้อนุมัติยกเลิกได้ทุกเมื่อจนกว่าการจองจะจบ |
| 7 | การแจ้งผล | แจ้งเตือนในระบบทุกขั้น ผู้อนุมัติได้รับแจ้งเมื่อมีการจองรออนุมัติ อีเมลเปิดภายหลังเมื่อตั้งค่า SMTP |
| 8 | ปฏิทิน | ทุกคนที่เข้าระบบเห็นทุกห้อง: เวลา สถานะ หัวข้อ ผู้จองและหน่วยงาน รายการเสริมและเหตุผลเห็นเฉพาะผู้จองและผู้อนุมัติ |
| 9 | สิทธิ์จัดการ | แยก `room-manager` (ตั้งค่าห้องและรายการเสริม) กับ `room-booking-approver` (พิจารณาและยกเลิก) |
| 10 | กติกา | ค่ากลางทั้งระบบ: 07:00–20:00 น. ทีละ 30 นาที, ล่วงหน้าไม่เกิน 90 วัน, ไม่ย้อนหลัง, ไม่เกิน 14 วันต่อการจอง, จำนวนผู้เข้าประชุมไม่เกินความจุ |
| 11 | การแก้ไข | แก้ไขไม่ได้หลังยื่น ต้องยกเลิกแล้วจองใหม่ ผู้อนุมัติมีเพียง อนุมัติ หรือ ไม่อนุมัติพร้อมเหตุผล |

## Domain model

ศัพท์ทั้งหมดอยู่ใน `CONTEXT.md` หมวด "ห้องประชุม"

- **ห้องประชุม** (`room`): ชื่อ, ที่ตั้งห้อง (ข้อความ เช่น "อาคารอำนวยการ ชั้น 2"), ความจุ, อุปกรณ์ประจำห้อง (ข้อความ), หน่วยงานเจ้าของทรัพยากร (`owner_organization_id`), เปิดให้จอง (`is_bookable`)
- **รายการเสริม** (`room_addon`): ชื่อ, หน่วยนับ (เช่น "เครื่อง", "ชุด"), เปิดใช้ (`is_active`) ใช้ได้กับทุกห้อง
- **การจองห้อง** (`room_booking`): เลขอ้างอิง, ห้อง, ผู้จอง, หน่วยงานของผู้จอง ณ เวลายื่น, หัวข้อการประชุม, จำนวนผู้เข้าประชุม, เวลาเริ่ม/สิ้นสุดรายวัน (นาทีนับจากเที่ยงคืนเวลาไทย), สถานะ
- **วันที่จอง** (`room_booking_day`): หนึ่งแถวต่อวัน มี `starts_at`/`ends_at` เป็น UTC และสถานะ `ACTIVE` หรือ `RELEASED` แถวเหล่านี้คือสิ่งที่ปฏิทินและการตรวจทับซ้อนใช้
- **รายการเสริมที่ขอ** (`room_booking_addon`): รายการเสริม, จำนวน, หมายเหตุ ถูกตรึงชื่อและหน่วยนับไว้ ณ เวลายื่น
- **ประวัติการจอง** (`room_booking_history`): ทุกการเปลี่ยนสถานะ ผู้กระทำ เวลา และเหตุผล (เหตุผลเก็บที่นี่เท่านั้น ไม่อยู่ในบันทึกการตรวจสอบหรือการแจ้งเตือน)

### Booking status

```
PENDING ──อนุมัติ──▶ APPROVED
   │                    │
   ├──ไม่อนุมัติ──▶ REJECTED
   └──ยกเลิก──▶ CANCELLED ◀──ยกเลิก──┘
```

- `PENDING` (รออนุมัติ) และ `APPROVED` (อนุมัติแล้ว) กันช่วงเวลา
- `REJECTED` และ `CANCELLED` ไม่กันช่วงเวลา
- "คืนวันที่เหลือ" ไม่เปลี่ยนสถานะการจอง แต่เปลี่ยนวันที่ยังไม่เริ่มเป็น `RELEASED` และบันทึกประวัติ
- "สิ้นสุดแล้ว" แสดงจากเวลา (วันสุดท้ายที่ `ACTIVE` จบแล้ว) ไม่เก็บเป็นสถานะ

## Rules

ทุกข้อตรวจที่ server ใน `packages/core` และคืน error code ที่หน้าจอแปลเป็นข้อความไทย

**การยื่นจอง** (ผู้ที่เข้าระบบแล้วทุกคน)
- เลือกห้องที่ `is_bookable`, รายการวันที่ (เวลาไทย) 1–14 วัน ไม่ซ้ำ, เวลาเริ่ม/สิ้นสุดเดียวกันทุกวัน
- เวลาอยู่ใน 07:00–20:00 ลงที่ :00 หรือ :30 และเริ่มก่อนสิ้นสุด → `INVALID_TIME_RANGE`
- วันแรกเริ่มหลังเวลาปัจจุบัน และวันสุดท้ายไม่เกิน 90 วันนับจากวันนี้ → `OUTSIDE_BOOKING_WINDOW`
- จำนวนผู้เข้าประชุม 1..ความจุห้อง → `OVER_CAPACITY`
- รายการเสริมต้อง `is_active` จำนวน 1–999 หมายเหตุไม่เกิน 500 ตัวอักษร → `INVALID_ADDON`
- หัวข้อ 1–200 ตัวอักษร
- ทับซ้อน: วันใดที่ `starts_at < ใหม่.ends_at AND ends_at > ใหม่.starts_at` กับวัน `ACTIVE` ของการจอง `PENDING`/`APPROVED` ของห้องเดียวกัน → `BOOKING_CONFLICT` พร้อมรายการวันที่ชน (วันที่และเวลาเท่านั้น ไม่เปิดเผยผู้จองใน error)

**การพิจารณา** (`room-booking-approver` ในขอบเขตหน่วยงานเจ้าของห้อง)
- ทำได้เมื่อสถานะ `PENDING` และยังมีวัน `ACTIVE` ที่ยังไม่สิ้นสุด → `BOOKING_NOT_PENDING`
- ผู้อนุมัติพิจารณาการจองของตนเองไม่ได้ → `CONFLICT_OF_INTEREST`
- ไม่อนุมัติต้องมีเหตุผล 1–1000 ตัวอักษร → `REASON_REQUIRED`

**การยกเลิก** (เหตุผล 1–1000 ตัวอักษรเสมอ)
- ผู้จอง, สถานะ `PENDING`/`APPROVED`, ก่อนวันแรกเริ่ม → ยกเลิกทั้งชุด สถานะ `CANCELLED`
- ผู้จอง, สถานะ `APPROVED`, วันแรกเริ่มแล้ว → คืนวันที่ยังไม่เริ่ม ถ้าไม่มีวันเหลือ → `NOTHING_TO_RELEASE`
- ผู้อนุมัติ, สถานะ `PENDING`/`APPROVED`, ก่อนวันสุดท้ายสิ้นสุด → ถ้ายังไม่เริ่มยกเลิกทั้งชุด ถ้าเริ่มแล้วคืนวันที่ยังไม่เริ่ม
- นอกเหนือจากนี้ → `CANCEL_NOT_ALLOWED`

**การจัดการห้องและรายการเสริม** (`room-manager` ในขอบเขตหน่วยงานเจ้าของห้อง)
- สร้าง แก้ไข ปิด/เปิดการจอง ไม่มีการลบ การปิดห้องไม่ยกเลิกการจองเดิม (หน้าจอเตือนจำนวนการจองที่ยังไม่จบ)
- ลดความจุไม่กระทบการจองเดิม

## Concurrency and transactions

ทุกการกระทำที่เปลี่ยนสถานะทำใน transaction เดียว: แถวธุรกิจ + `room_booking_history` + `audit_event` + `outbox_event`

การกันทับซ้อน: transaction การยื่นจอง `SELECT ... FROM room WHERE id = ? FOR UPDATE` ก่อนตรวจทับซ้อนแล้วจึง insert ทำให้การจองห้องเดียวกันเรียงคิวกัน ห้องต่างกันไม่รอกัน การพิจารณาและยกเลิกล็อกแถว `room_booking` ด้วย `FOR UPDATE` เพื่อไม่ให้สองคนตัดสินพร้อมกัน

เลขอ้างอิง `RB-<ปี พ.ศ.>-<ลำดับ 4 หลัก>` เช่น `RB-2569-0001` ออกจากตาราง `room_booking_sequence` (หนึ่งแถวต่อปี, `FOR UPDATE`) ในธุรกรรมเดียวกัน ปีคิดจากวันที่ยื่นตามเวลาไทย

## Authorization

- permission ใหม่: `room.manage`, `room.booking.decide` เพิ่มใน `permissionSchema` และ `policy.ts`: `room-manager → room.manage`, `room-booking-approver → room.booking.decide`
- resource ของทุกการกระทำของผู้จัดการ/ผู้อนุมัติคือ `{ moduleCode: 'room-booking', organizationId: room.owner_organization_id }` บทบาทที่มอบแบบไม่ระบุหน่วยงานใช้ได้ทุกห้อง
- การยื่นจอง ดูปฏิทิน และดูการจองของตนใช้แค่ session ที่ยืนยันตัวตนแล้ว
- รายละเอียดการจอง (รายการเสริม ประวัติ เหตุผล) ดูได้เฉพาะผู้จอง หรือผู้ถือ `room.booking.decide` ในขอบเขตห้องนั้น นอกนั้นตอบ 404
- เมนู "ห้องประชุม" แสดงทุกคน, "รออนุมัติ" แสดงเมื่อมี `room-booking-approver`, "จัดการห้อง" แสดงเมื่อมี `room-manager` แต่ API ตรวจสิทธิ์เองทุกครั้ง

## Notifications

ใช้ outbox `notification.in_app` เดิม ข้อความไม่มีเหตุผลและไม่มีชื่อผู้จอง

| เหตุการณ์ | ผู้รับ | ข้อความ |
|---|---|---|
| ยื่นจอง | ผู้จอง | `ยื่นจองห้องแล้ว รออนุมัติ (RB-…)` |
| ยื่นจอง | ผู้ถือ `room-booking-approver` ทุกคนที่มีขอบเขตห้องนั้น (ยกเว้นผู้จอง) | `มีการจองห้องรออนุมัติ (RB-…)` |
| อนุมัติ | ผู้จอง | `การจองห้องได้รับอนุมัติ (RB-…)` |
| ไม่อนุมัติ | ผู้จอง | `การจองห้องไม่ได้รับอนุมัติ (RB-…)` |
| ผู้อนุมัติยกเลิก/คืนวัน | ผู้จอง | `การจองห้องถูกยกเลิกโดยผู้ดูแล (RB-…)` |
| ผู้จองยกเลิกการจองที่อนุมัติแล้ว/คืนวัน | ผู้อนุมัติที่พิจารณาการจองนั้น | `ผู้จองยกเลิกการจองห้อง (RB-…)` |

การแจ้งเตือนต้องลิงก์ไปหน้ารายละเอียดการจอง ไม่ใช่หน้าคำขอ: migration เพิ่มคอลัมน์ `notification.target_path` (nullable, เช่น `/rooms/bookings/<uuid>`), `notificationEventPayloadSchema` รับ `requestId` หรือ `targetPath` อย่างใดอย่างหนึ่ง และหน้าการแจ้งเตือนเปิด `targetPath` ถ้ามี มิฉะนั้นใช้ `/requests/<requestId>` เหมือนเดิม `targetPath` ต้องขึ้นต้นด้วย `/` และไม่มี `//` เพื่อไม่ให้เป็นลิงก์ออกนอกระบบ

## Audit

action: `room.created`, `room.updated`, `room_addon.created`, `room_addon.updated`, `room_booking.submitted`, `room_booking.approved`, `room_booking.rejected`, `room_booking.cancelled`, `room_booking.days_released`
metadata: `bookingReference`, `roomId`, `status`, `dayCount` เท่านั้น ห้ามมีหัวข้อการประชุม เหตุผล หรือหมายเหตุ

## Screens

ทั้งหมดอยู่ใต้ `apps/web/src/app/(app)/rooms` และใช้ AppShell เดิม (เข้าผ่านหน้าหลัก Back Office) เวลาทั้งหมดแสดงเป็น Asia/Bangkok ปี พ.ศ.

- `/rooms` ปฏิทินห้องประชุม: มุมมองสัปดาห์ (ค่าเริ่มต้น) และวัน, กรองห้อง, แถบแต่ละการจองแสดงเวลา หัวข้อ ผู้จอง หน่วยงาน และป้ายสถานะเป็นข้อความ (รออนุมัติ/อนุมัติแล้ว) ไม่ใช้สีอย่างเดียว ปุ่ม "จองห้อง"
- `/rooms/bookings/new` แบบฟอร์มจอง: ห้อง, วันเริ่ม–วันสิ้นสุด แล้วติ๊กเว้นวันได้, เวลาเริ่ม/สิ้นสุด, หัวข้อ, จำนวนผู้เข้าประชุม, รายการเสริม; เมื่อชนแสดงวันที่ชนใต้ฟอร์ม
- `/rooms/bookings` การจองของฉัน: แยก กำลังจะมาถึง / ที่ผ่านมา
- `/rooms/bookings/[bookingId]` รายละเอียด: ข้อมูลการจอง รายวัน รายการเสริม ประวัติพร้อมเหตุผล ปุ่มยกเลิก/คืนวันที่เหลือ (ผู้จอง) และ อนุมัติ/ไม่อนุมัติ/ยกเลิก (ผู้อนุมัติ) ตามที่กติกาอนุญาต
- `/rooms/approvals` รายการรออนุมัติ เรียงตามวันเริ่มใช้ห้อง
- `/rooms/manage` จัดการห้องและรายการเสริม

API routes ใต้ `apps/web/src/app/api/rooms/...` เรียก service ใน `packages/core/src/rooms` และแปลง error code เป็น HTTP (400 validation, 403 สิทธิ์, 404 ไม่พบ/ไม่มีสิทธิ์ดู, 409 ทับซ้อนหรือสถานะไม่ถูกต้อง)

## Components and interfaces

- `packages/contracts/src/rooms.ts`: zod schemas `submitRoomBookingInputSchema`, `decideRoomBookingInputSchema`, `cancelRoomBookingInputSchema`, `roomInputSchema`, `roomAddonInputSchema`, ชนิดสถานะ และค่ากติกา `roomBookingPolicy`
- `packages/core/src/rooms/booking-days.ts`: ฟังก์ชันบริสุทธิ์ แปลงวันที่ไทย + นาที เป็นช่วง UTC และตรวจกติกาเวลา
- `packages/core/src/rooms/room-booking-service.ts`: `submit`, `decide`, `cancel` รับ `actor: { personId, roles }` และ `now` จากภายนอก ใช้ `RoomBookingRepository` (transaction, lock, save, outbox, audit, history)
- `packages/core/src/rooms/room-catalog-service.ts`: จัดการห้องและรายการเสริม
- `packages/core/src/rooms/database-room-booking-repository.ts`: SQL บน MariaDB
- `packages/core/src/rooms/room-calendar-query.ts`: อ่านปฏิทินตามช่วงวัน คืนเฉพาะฟิลด์สาธารณะ
- `packages/db/migrations/0004_room_booking.sql` + `packages/db/src/schema/rooms.ts` + เพิ่มใน `migrate.ts` และสคริปต์ restore-verify
- `apps/web/src/lib/actor.ts`: `requireActor(request)` คืน `{ personId, roles }` จาก session ปัจจุบัน เป็นจุดเชื่อมเดียวที่โมดูลห้องประชุมรู้จัก (ดู ADR 0002)

## Out of scope
