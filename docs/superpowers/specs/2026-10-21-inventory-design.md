# Inventory Design (R2 คลังพัสดุ)

**Status:** approved 2026-10-21
**Date:** 2026-10-21
**Source:** คำขอของผู้ใช้ในเธรด "ระบบคลังพัสดุ" และการสัมภาษณ์ออกแบบ 12 ข้อ (2026-10-21), แผนแม่บท `2026-09-30-waritch-hospital-back-office-design.md` (R2 Inventory), กติกาการเชื่อมระบบ `docs/integration/modules.md`

## Purpose

ให้งานพัสดุบริหารคลังวัสดุกลางของโรงพยาบาลได้ครบวงจรใน Back Office: ทะเบียนวัสดุ รับเข้า ยอดคงเหลือตามล็อต สั่งซื้อ และจ่ายออกตามใบขอเบิกของหน่วยงาน โดยยอดคงเหลือ มูลค่า และวันหมดอายุถูกต้องตรวจสอบย้อนหลังได้ และหน่วยงานขอเบิกได้เฉพาะของที่มีในคลัง

เอกสารนี้กำหนดภาพรวมของทั้งโมดูล และลงรายละเอียดเฉพาะ **รอบที่ 1** รอบที่ 2–4 จะมี spec ของตัวเองต่อจากเอกสารนี้

## Decisions from the interview

| # | เรื่อง | ข้อสรุป |
|---|---|---|
| 1 | รูปแบบคลัง | คลังกลางแห่งเดียวของงานพัสดุ ไม่ติดตามยอดที่หน่วยงานหลังจ่ายออก |
| 2 | การสั่งซื้อ | ใบสั่งซื้ออย่างง่าย: ระบบเสนอรายการที่ต่ำกว่าจุดสั่งซื้อ งานพัสดุออกใบสั่งซื้อพร้อมผู้ขายและราคา รับเข้าอ้างอิงใบสั่งซื้อได้ทั้งครบและบางส่วน ขั้นตอนจัดซื้อจัดจ้างตามระเบียบและ e-GP ทำนอกระบบ |
| 3 | ยอดที่ขอเบิกได้ | ไม่จองยอด ตรวจกับยอดคงเหลือตอนส่งใบขอเบิก ถ้าตอนจ่ายของไม่พอ งานพัสดุจ่ายบางส่วนได้ |
| 4 | การอนุมัติใบขอเบิก | หัวหน้าหน่วยงานของผู้ขออนุมัติผ่านสายอนุมัติกลางของ **คำขอ** แล้วเข้าคิวงานพัสดุ |
| 5 | ล็อตและมูลค่า | ติดตามตามล็อต มีวันหมดอายุเมื่อวัสดุนั้นมีอายุ จ่ายออกแบบ FIFO คิดมูลค่าตามราคาของล็อต |
| 6 | หน่วยนับ | หน่วยซื้อกับหน่วยเบิกต่างกันได้ พร้อมอัตราแปลง ยอดคงเหลือเก็บเป็นหน่วยเบิก |
| 7 | ข้อมูลตั้งต้น | คีย์ทะเบียนวัสดุและยอดยกมาบนหน้าจอ ไม่มีการนำเข้าไฟล์ หัวหน้างานพัสดุรับรองยอดยกมา |
| 8 | อุปกรณ์สแกน | ทั้งเครื่องสแกน USB/Bluetooth แบบคีย์บอร์ด และกล้องมือถือ/แท็บเล็ตผ่านเบราว์เซอร์ |
| 9 | รหัสที่สแกน | บาร์โค้ดผู้ผลิต (ผูกได้หลายรหัสต่อวัสดุ) และฉลาก QR ต่อล็อตที่ระบบพิมพ์ตอนรับเข้า |
| 10 | การปรับยอด | ปรับรายล็อตพร้อมเหตุผล หัวหน้างานพัสดุอนุมัติก่อนยอดเปลี่ยน การตรวจนับทั้งคลังไว้รุ่นถัดไป |
| 11 | รายงาน | ยอดคงเหลือและมูลค่า บัญชีวัสดุ รายการต่ำกว่าจุดสั่งซื้อ ใกล้หมดอายุ สรุปการจ่ายรายเดือนตามหน่วยงาน ดาวน์โหลด CSV ได้ บัญชีวัสดุพิมพ์เป็น PDF ตามแบบฟอร์มราชการ และแจ้งเตือนเจ้าหน้าที่พัสดุวันละครั้ง |
| 12 | การแบ่งรอบและสิทธิ์ | 4 รอบตามด้านล่าง; บุคลากรทุกคนขอเบิกได้, เจ้าหน้าที่พัสดุทำทะเบียน รับเข้า จ่ายออก สั่งซื้อ, หัวหน้างานพัสดุรับรองยอดยกมาและอนุมัติการปรับยอด |

## Module-wide model

ศัพท์ทั้งหมดอยู่ใน `CONTEXT.md` หมวด "คลังพัสดุ" ตารางทั้งหมดขึ้นต้นด้วย `inventory_` และอ้างอิงบุคลากรด้วย `person.id`

- **วัสดุ** (`inventory_item`) คือสิ่งที่เก็บในคลังและขอเบิกได้ ยอดคงเหลือทุกที่เป็น **หน่วยเบิก** เป็นจำนวนเต็ม
- **ล็อต** (`inventory_lot`) คือวัสดุหนึ่งชุดที่รับเข้าพร้อมกันด้วยราคาและวันหมดอายุเดียวกัน ล็อตเป็นหน่วยเล็กที่สุดของยอดคงเหลือและมูลค่า
- **รายการเคลื่อนไหว** (`inventory_movement`) คือบัญชีที่เพิ่มอย่างเดียว ไม่มีแก้ไขหรือลบ ทุกการเปลี่ยนยอดของล็อตเขียนหนึ่งแถว จำนวนมีเครื่องหมาย (+ รับเข้า, − จ่ายออก/ยกเลิก/ปรับลด) และตรึงราคาต่อหน่วยของล็อตไว้
- `inventory_lot.on_hand_quantity` เป็นยอดที่เก็บไว้เพื่ออ่านเร็ว เงื่อนไขที่ต้องเป็นจริงเสมอ: เท่ากับผลรวม `quantity` ของรายการเคลื่อนไหวของล็อตนั้น และไม่ติดลบ
- ลำดับการจ่ายออก (ใช้ในรอบ 2): ล็อตที่มีวันหมดอายุก่อนออกก่อน ล็อตที่ไม่มีวันหมดอายุหรือวันเดียวกันเรียงตามเวลารับเข้า (FIFO ที่คำนึงวันหมดอายุ) ล็อตที่หมดอายุแล้วไม่ถูกเสนอให้จ่าย
- มูลค่าคงเหลือ = ผลรวมของ `on_hand_quantity × unit_cost` ของแต่ละล็อต

**ตัวเลข:** `entered_quantity` และ `issue_quantity` เป็นจำนวนเต็ม `issue_quantity = entered_quantity × unit_factor` (เมื่อป้อนเป็นหน่วยซื้อ) `line_total = entered_quantity × entered_unit_price` ปัด 2 ตำแหน่ง `unit_cost = line_total / issue_quantity` เก็บ 4 ตำแหน่ง ราคา 0 ได้ (ของบริจาค) ห้ามติดลบ

**เลขอ้างอิง:** ใบรับเข้า `RC-<พ.ศ.>-<ลำดับ 4 หลัก>`, ยอดยกมา `OB-<พ.ศ.>-0001`, ล็อต `LT-<พ.ศ.>-<ลำดับ 6 หลัก>` ปีคิดจากวันที่บันทึกตามเวลาไทย

### Receipt status

```
ใบรับเข้า (DELIVERY):   POSTED ──ยกเลิก──▶ VOIDED

ยอดยกมา (OPENING):      DRAFT ──ส่งรับรอง──▶ SUBMITTED ──รับรอง──▶ CERTIFIED
                          ▲                      │
                          └────ส่งกลับแก้ไข──────┘
```

- ใบรับเข้าบันทึกแล้วเป็น `POSTED` ทันที ไม่มีร่าง (ฟอร์มเก็บร่างไว้ในเบราว์เซอร์จนกดบันทึก)
- ยอดยกมามีได้ใบเดียวทั้งระบบ สร้างครั้งแรกเมื่อเปิดหน้ายอดยกมา แก้ไขบรรทัดได้เฉพาะ `DRAFT` ล็อตและรายการเคลื่อนไหว `OPENING` ถูกสร้างตอน `CERTIFIED` เท่านั้น
- หลัง `CERTIFIED` ยอดยกมาแก้ไม่ได้ การแก้ยอดทำผ่านการปรับยอด (รอบ 3)

### Rules

ทุกข้อตรวจที่ server ใน `packages/core/src/inventory` และคืน error code ที่หน้าจอแปลเป็นข้อความไทย

**ทะเบียน** (`inventory.item.manage`)
- รหัสวัสดุ ชื่อผู้ขาย ชื่อหมวด และบาร์โค้ดซ้ำไม่ได้ → `DUPLICATE_CODE`, `DUPLICATE_NAME`, `DUPLICATE_BARCODE` (บอกว่าบาร์โค้ดนั้นผูกกับวัสดุรหัสใด)
- บาร์โค้ดต้องไม่ขึ้นต้นด้วย `LT-` เพื่อไม่ชนกับฉลากล็อต → `INVALID_BARCODE`
- ปิดใช้วัสดุได้แม้ยังมียอดคงเหลือ (หน้าจอเตือนยอดที่เหลือ) วัสดุที่ปิดใช้รับเข้าไม่ได้ → `ITEM_INACTIVE`
- เปลี่ยน `tracks_expiry` ไม่ได้เมื่อวัสดุมีล็อตแล้ว → `ITEM_HAS_LOTS`

**ยอดยกมา**
- เพิ่ม แก้ ลบ บรรทัด และส่งรับรอง: `inventory.stock.receive` สถานะ `DRAFT` เท่านั้น → `OPENING_NOT_EDITABLE`; ส่งรับรองต้องมีอย่างน้อย 1 บรรทัด → `EMPTY_RECEIPT`
- รับรองหรือส่งกลับ: `inventory.opening.certify` สถานะ `SUBMITTED` เท่านั้น → `OPENING_NOT_SUBMITTED`; ส่งกลับต้องมีเหตุผล 1–1000 ตัวอักษร → `REASON_REQUIRED`
- ก่อนยอดยกมา `CERTIFIED` บันทึกใบรับเข้าไม่ได้ → `OPENING_NOT_CERTIFIED` เพื่อให้ยอดเปิดระบบเป็นจุดเริ่มต้นของบัญชีทุกวัสดุ
- ไม่ห้ามผู้รับรองเป็นคนเดียวกับผู้ส่ง (งานพัสดุมีคนน้อย) แต่บันทึกทั้งสองคนในประวัติ

**บรรทัดรับเข้า** (ทั้งยอดยกมาและใบรับเข้า)
- วัสดุต้อง `is_active`; จำนวน 1–1,000,000; ราคาต่อหน่วย 0–10,000,000 → `INVALID_LINE`
- วัสดุที่ `tracks_expiry` ต้องมีวันหมดอายุ และ (สำหรับใบรับเข้า) ต้องหลัง `received_on` → `EXPIRY_REQUIRED`, `EXPIRY_IN_PAST`; วัสดุที่ไม่ `tracks_expiry` ห้ามใส่วันหมดอายุ
- ใบหนึ่งมี 1–200 บรรทัด วัสดุเดียวกันอยู่หลายบรรทัดได้ (คนละล็อต)

**ใบรับเข้า** (`inventory.stock.receive`)
- `received_on` ไม่อยู่ในอนาคต และไม่ก่อนวันที่รับรองยอดยกมา → `INVALID_RECEIVED_DATE`
- ผู้ขายต้อง `is_active` → `VENDOR_INACTIVE`
- ยกเลิกได้เมื่อ `POSTED` และทุกล็อตของใบยังมี `on_hand_quantity = received_quantity` (ยังไม่ถูกจ่ายหรือปรับ) ต้องมีเหตุผล → `RECEIPT_NOT_VOIDABLE`; ผลคือรายการเคลื่อนไหว `RECEIPT_VOID` ลบยอดทุกล็อตเป็น 0 และสถานะ `VOIDED`

### Scanning

ช่องสแกนเดียวใช้ทั้งหน้ารับเข้า ยอดยกมา และยอดคงเหลือ (รอบ 2 ใช้ซ้ำที่หน้าจ่ายออก)

- **เครื่องสแกน:** ช่องรับข้อความที่ focus อยู่ เครื่องสแกนพิมพ์รหัสแล้วกด Enter ระบบค้นหาทันที และล้างช่องรอสแกนต่อ
- **กล้อง:** ปุ่ม "สแกนด้วยกล้อง" เปิดกล้องหลังผ่าน `getUserMedia` และถอดรหัส EAN-13, EAN-8, UPC-A, Code 128, Code 39 และ QR ด้วยไลบรารีฝั่งเบราว์เซอร์ (`@zxing/browser`) ต้องเปิดผ่าน HTTPS (มีโปรไฟล์ LAN HTTPS แล้ว) ถ้าเบราว์เซอร์ไม่อนุญาตกล้อง แสดงข้อความและยังพิมพ์รหัสได้
- **การค้นหา** (`GET /api/inventory/scan?code=`, ต้องมี `inventory.stock.read` หรือ `inventory.stock.receive`): ลำดับคือ รหัสล็อต (`LT-…`) → บาร์โค้ดผู้ผลิต → รหัสวัสดุ ตรงทั้งคำ คืน `{ kind: 'lot' | 'barcode' | 'item', item, unitKind?, lot? }` หรือ 404 `CODE_NOT_FOUND` หน้าจอเสนอ "ผูกบาร์โค้ดนี้กับวัสดุ" ให้ผู้ถือ `inventory.item.manage`
- **ในหน้ารับเข้า:** สแกนวัสดุที่ยังไม่มีในใบ เพิ่มบรรทัดใหม่ด้วยหน่วยตามบาร์โค้ด สแกนซ้ำวัสดุเดียวกันเพิ่มจำนวนของบรรทัดล่าสุดของวัสดุนั้นทีละ 1 สแกนฉลากล็อตในหน้ารับเข้าแสดงข้อความว่าเป็นของที่รับเข้าแล้ว

### QR labels

- หน้า `/inventory/receipts/[receiptId]/labels` (และของยอดยกมา) แสดงฉลากหนึ่งชุดต่อล็อต ผู้ใช้กำหนดจำนวนฉลากต่อล็อตได้ (ค่าเริ่มต้น 1, สูงสุด 500)
- QR เข้ารหัสเฉพาะ `lot_code` ฉลากแสดง QR, ชื่อวัสดุ, รหัสวัสดุ, รหัสล็อต, วันหมดอายุ (ถ้ามี) และวันที่รับเข้า ไม่มีราคาหรือชื่อผู้ขาย
- สร้าง QR เป็น SVG ฝั่ง server ด้วยไลบรารี `qrcode` และพิมพ์ด้วยปุ่ม "พิมพ์ฉลาก" (`window.print()`)
- รูปแบบกระดาษ 2 แบบให้เลือก: A4 สติกเกอร์ 3 × 8 ดวง (ค่าเริ่มต้น) และเครื่องพิมพ์ฉลากความร้อน 50 × 30 มม. หนึ่งดวงต่อหน้า

### Authorization

- permission ใหม่ใน `permissionSchema` และ `policy.ts`:
  - `inventory-officer` (เจ้าหน้าที่พัสดุ) → `inventory.item.manage`, `inventory.stock.receive`, `inventory.stock.read`
  - `inventory-supervisor` (หัวหน้างานพัสดุ) → `inventory.opening.certify`, `inventory.stock.read`
- คลังเป็นของทั้งโรงพยาบาล ทุกการกระทำตรวจด้วย `AuthorizationService.canActHospitalWide(subject, permission, 'inventory')` บทบาทที่มอบแบบระบุหน่วยงานไม่ให้สิทธิ์ในโมดูลนี้
- รอบ 1 ไม่มีหน้าสำหรับบุคลากรทั่วไป ปุ่มโมดูลจึงแสดงเฉพาะผู้ถือบทบาทพัสดุ (รอบ 2 เพิ่มเมนู "ขอเบิก" ให้ทุกคน)
- API ตอบ 401 เมื่อไม่ได้เข้าระบบ 403 เมื่อไม่มีสิทธิ์ 404 เมื่อไม่พบ

### Concurrency and transactions

- ทุกการเปลี่ยนสถานะเขียน แถวธุรกิจ + ประวัติ + รายการเคลื่อนไหว + `audit_event` + `outbox_event` ในธุรกรรมเดียว
- ยอดยกมาและใบรับเข้าล็อกแถวใบด้วย `SELECT … FOR UPDATE` ก่อนตรวจสถานะ การยกเลิกใบรับเข้าล็อกล็อตทั้งหมดของใบด้วย `FOR UPDATE` ก่อนตรวจยอด (รอบ 2 จะล็อกล็อตแบบเดียวกันตอนจ่าย จึงไม่ชนกัน)
- เลขอ้างอิงและรหัสล็อตออกจาก `inventory_sequence` ด้วย `FOR UPDATE`

### Components and interfaces

- `packages/contracts/src/inventory.ts`: zod schemas ของวัสดุ หมวด ผู้ขาย บาร์โค้ด บรรทัดรับเข้า ใบรับเข้า ยอดยกมา การตัดสินยอดยกมา การยกเลิก, ชนิดสถานะ และค่าจำกัด `inventoryLimits`
- `packages/core/src/inventory/quantities.ts`: ฟังก์ชันบริสุทธิ์ แปลงหน่วย คำนวณ `issue_quantity`, `line_total`, `unit_cost` และลำดับการจ่ายของล็อต
- `packages/core/src/inventory/catalog-service.ts`: หมวด วัสดุ บาร์โค้ด ผู้ขาย
- `packages/core/src/inventory/receipt-service.ts`: `postDelivery`, `voidDelivery`, `saveOpeningLines`, `submitOpening`, `returnOpening`, `certifyOpening` รับ `actor` และ `now` จากภายนอก ใช้ `InventoryRepository`
- `packages/core/src/inventory/inventory-repository.ts` (interface), `in-memory-inventory-repository.ts` (unit test), `database-inventory-repository.ts` (MariaDB)
- `packages/core/src/inventory/inventory-queries.ts`: ยอดคงเหลือ รายละเอียดวัสดุ การค้นหารหัสสแกน
- `apps/web/src/app/api/inventory/...` route ที่เรียก service และแปลง error code เป็น HTTP (400 validation, 403, 404, 409 สถานะ/ซ้ำ)
- `apps/web/src/app/(app)/inventory/scan-field.tsx`: ช่องสแกนที่ใช้ซ้ำได้ (คีย์บอร์ด + กล้อง)
