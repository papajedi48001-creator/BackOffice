# Smart Money round 3: ติดตามกองทุนย่อย FDH Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the legacy `modules/fdh_monitor` pages into BackOffice at `/money/fdh` and `/money/fdh/files`, with the same
numbers and screens.

**Architecture:** As round 2. The browser reads REP/STM Excel files with SheetJS and posts the used sheets as arrays of rows.
The server parses them with a TypeScript port of `FdhRepParser`/`FdhStmParser` and keeps one row per (kind, doc_no) in
`money_fdh_document`, the parsed document encrypted with the national-ID key. The dashboard loads every document and computes
everything in the browser with a TypeScript port of `fdh-core.js`.

**Tech Stack:** Next.js App Router, zod, MariaDB + Drizzle, vitest, `@e965/xlsx@0.20.3` (browser only), `NationalIdProtector`.

**Spec:** `docs/superpowers/specs/2026-11-18-smart-money-fdh-monitor-design.md`. Legacy: `modules/fdh_monitor/*`,
`tests/fdh/*` (PHP and node tests).

## Global Constraints
- Upload and delete need `money.manage`, checked on the server before the body is read. Viewing needs the `fdh` page tick or manage.
- Posted body ≤ 24 MB; ≤ 6 sheets, each ≤ 30,000 rows of ≤ 200 cells (strings ≤ 1,000 chars, finite numbers, booleans, null).
- Parsed documents are stored encrypted; no PID, name, doc_no or money in URL, log or audit.
- Audit: `money.fdh.upload` {kind, rows}, `money.fdh.remove` {kind}, `money.fdh.remove_all` {kind, documents}.
- Client components import only types from `@backoffice/core`. Popups close only from their buttons. Dates entered with
  `ThaiDateInput`, shown as `13 พ.ย. 2569`.

## Review Focus
1. A workbook that is neither REP nor STM, or a doc_no with other characters, is refused with the legacy Thai message.
2. Re-uploading the same (kind, doc_no) replaces it; REP and STM with the same doc_no are separate rows.
3. Without the national-ID keys, upload is refused and nothing is stored; the stored column never contains a PID in clear.
4. A member without the `fdh` tick gets 403 from GET; a non-manager gets 403 from POST/DELETE without the body being read.
5. Parser output equals legacy PHP output for the legacy test workbooks (fixtures generated by running the PHP parsers).

## Rulings during execution
- A REP `Detail` row runs to about 120 cells (SEQ NO is column 118), so the per-row limit is 200, not round 2's 80.
- Audit target_id is CHAR(36): FDH events use a 32-hex SHA-256 of `kind:doc_no`, which also keeps the เลขที่เอกสาร out of audit.
- Without the national-ID keys, upload answers `NOT_CONFIGURED` with a Thai message; reading stored documents does the same.
- Parity fixtures are generated by `fixtures/make-fdh-legacy.php` from the legacy PHP tests' synthetic workbooks, passed through JSON as the browser did.
- Dashboard rows open popups from a button in the row (VN, sub-fund, Error Code), not a clickable `<tr>` (DESIGN.md: no clickable div).
  The sub-fund chart is GroupedBarChart, which has no click; the sub-fund table's name button filters instead.
- The searches inside the dashboard tabs are exempt in `search-cards.test.ts` (the filters sit in the page's search-card), as NHSO.
- The FDH popup has its own frame (`.fdh-dialog`: fixed header with ปิด, scrolling body), because `.action-dialog` does not
  scroll and at 390 px pushed ปิด off screen (found by the screenshot run).
